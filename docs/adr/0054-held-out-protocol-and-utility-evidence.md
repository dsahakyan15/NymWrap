# Заморозка и статистика проверки связывания

Development и held-out имеют независимые синтетические профили и случайность.
Held-out создаётся только после заморозки кода, модели, настроек и завершённой
development-оценки. Изменение защиты после просмотра результата превращает этот
held-out в регрессию; для новой приёмки нужна новая невиденная часть.

Кандидат пользователя выбирается равномерно среди N досье, порядок случайный;
один эксперимент — один разговор с полной накопленной историей. Отдельные языки
и публичные контрольные задачи показываются отдельно. Полезность требует
проверки настоящего ответа по заранее заданному критерию; сохранение слов
в переписанном вопросе не считается полезным ответом. L0, ошибки и непроведённые
проверки не исчезают из знаменателя полезности.

Публикуются k/n, точный двусторонний интервал Clopper–Pearson 95% и односторонний
binomial P(X≥k | p=1/N). Значимое превышение при α=0.05 — провал, отсутствие
значимости не доказывает равенство вероятностей. До принятия результатов нужны
полные пары raw/outbound и подтверждение, что атакующий распознаёт исходные
приватные вопросы лучше случайного. Ошибка ответа атакующего и отсутствие
исходящих данных дают неизвестный результат. Публичные задачи не разбавляют
частную выборку: её top-1 проверяется отдельно. Интервалы описывают выбранный
синтетический генератор, не вероятность анонимности реального человека.

Формулы: [NIST §7.2.4.1](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm),
[SciPy binomtest](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.binomtest.html).
Собственная реализация без новой зависимости проверяется на опубликованных
численных примерах и граничных значениях. Freeze-проверка и слепая приёмка
остаются открытыми. Подготовлены 384
development-примера (EN 127 / RU 124 / HY 133), с 64 новыми синтетическими
досье на разговор, раздельными и накопленными фактами, Device/личными канарейками,
инъекциями и публичными задачами. Полезность этого генератора ограничена целой
арифметикой. Held-out ещё не создан; генератор CLI не принимает такой режим.

Development-evaluator privacy_linkcheck использует production Engine и общий
сборщик досье Workspace. Подтверждённые синтетические черты, личный секрет,
Device и сводка импорта проходят временное зашифрованное хранилище; ключи
теста находятся в mlock-памяти, хранилище удаляется через teardown. Настоящие
nw-llmd проверяют хеши моделей и peer image. Ответы L0 и симулированного
провайдера генерирует настоящая модель, без заглушки финального ответа.
Удалённых запросов, ключа провайдера и доступа к реальному workspace нет.

Атакующий делает принудительный top-1 выбор из 64 досье по полному видимому
разговору; отдельный буквальный matcher не позволяет скрыть простое связывание.
По ADR 0065 LLM выделяет наблюдаемые факты из полного словаря, а код ранжирует
все досье по их сочетанию и точным nonce. Оба атакующих используют все факты
кандидатов, но не индекс субъекта или правильный ответ.
Ошибка JSON/модели — невалидная атака. Задача считается полезной только если
каждый настоящий ответ — заранее заданное целое число. Сформированный запрос
считается раскрытым ещё до ответа провайдера, включая ошибку этого ответа.
Канарейки проверяются в сформированных байтах. Это не OS pcap и не измерение
произвольных полезных задач. Единичный правильный случайный top-1 попадает в
список для разбора, а сам по себе не объявляется доказанной утечкой.

Модель использует фиксированную грамматику linkage_facts_v1 (до 26 букв);
дубли/неизвестные буквы отвергает код. Старая linkage_v1 остаётся форматом
внутренней совместимости, её не используют для новой оценки. CPU/private-IPC
тест проверяет форматы, а не точность. Словарь и короткие строки кандидатов
сохраняют полные факты; случайные nonce сопоставляет атакующий код. Unit-тест
восстанавливает все факты и проверяет каждое совпадение. Ошибки времени и
вычисления остаются невалидными атаками, их нельзя заменять случайной догадкой.

scripts/linkcheck-eval.mjs закрепляет копии бинарников и хеши корпуса, модели,
политики и скриптов. Политика профиля берётся из кода, технический endpoint в
ней заменяется синтетическим, чтобы не публиковать digest SID или путь домой.
Частичный checkpoint можно продолжить только с той же provenance; он никогда
не принимается за полный. Отчёты двух атакующих и точные интервалы считаются
только после завершения всех случаев. Даже полный development-отчёт явно
сохраняет статус «приёмка не выполнена» до заморозки и нового held-out.

Отдельный workflow privacy-development запускает 1 диагностический случай или
полные 384 на Ubuntu с настоящими закреплёнными моделями. Pilot не закрывает
этап. Невалидный атакующий прерывает CI с failed/incomplete. Полный development
дополнительно требует нулевых канареек, проверки обоих атакующих и каждого
языка, калибровки raw-атакующего в каждой паре язык/приватная группа. Эта проверка всё ещё
не является held-out приёмкой. Её fixtures отдельно ловят all-L0, отсутствие
одного языка и атакующего, который умеет только распознавать канарейки.
