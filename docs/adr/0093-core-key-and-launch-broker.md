# Минимальный брокер ключей и запуска для изоляции core

Статус: согласовано направление; дизайн, реализация отложена. M6 открыт.

## Контекст

LPAC из ADR 0092 не имеет доступа к Credential Manager. Core сейчас обращается
к нему через nw-vault/nw-cred и сам запускает workers. Добавление core прав
обычного AppContainer или доступа к хранилищу нарушило бы требуемую границу.
Отдельный процесс с обычным пользовательским токеном тоже не доказывает
отсутствие сети. Изолированные API, model workers и cover relay уже реализованы
отдельным коммитом; этот ADR не объявляет core или брокер изолированными.

## Решение

Core должен остаться в LPAC без сети, Credential Manager и права spawn.
Минимальный брокер получает только две операции по аутентифицированному IPC:
выдать ключ разрешённого домена текущей полосы и запустить worker по фиксированному
профилю из репозитория через nw-sandbox. Это не общий Credential Manager API,
shell, файловый сервер или произвольный process launcher.

Одна полоса соответствует одному экземпляру брокера и отдельному IPC capability.
Cover не получает vault, shadow history, master/root key или право запускать
shadow-профиль. Запрос содержит закрытые enum домена/профиля и ограниченные
типизированные параметры. Пути бинарников, имена credentials, аргументы,
окружение, наследуемые handles и ACL выбирает брокер по локальному manifest,
а не по строкам клиента. Profile.Model сохраняет одноразовый процесс,
read-only GGUF, deadline/memory/job limits ADR 0029/0092.

Свежий session key передаётся только по приватному наследуемому bootstrap.
Протокол переиспользует проверку владельца, kernel PID, challenge, AEAD,
sequence и роли core RPC; у полос разные ключи и endpoints. Авторизация привязана
к удерживаемому process handle/pidfd и зарегистрированному bootstrap, не к
одному числу PID или доступности pipe. Запущенные children остаются собственностью
брокера: EOF/отзыв сессии/timeout уничтожают job или сохранённое дерево bwrap.
Ответ о запуске не позволяет передать произвольный PID как доверенный peer.
Должен быть определён приватный канал от брокера к worker и проверяемая core
идентичность worker: текущую проверку «kernel PID равен PID родителя core» нельзя
просто отключить при смене родителя на брокер.

Ключи живут только в памяти в LockedKey/secrecy/zeroize; временные кадры очищаются,
размеры ограничены, секреты не попадают в argv, environment, файлы или журналы.
Ошибка memory-lock, Credential Manager, аутентификации или профиля прекращает
операцию. Нет повторного запуска core с более широким токеном. Журнал содержит
только тип события, время и фиксированный код ошибки.

## Обязательные границы перед реализацией

`nw-vault::Store` v1 хранит в Credential Manager OS-секрет для KDF, а случайные
доменные ключи — в зашифрованном root.nwenc. Поэтому операция «выдать доменный
ключ из Credential Manager» ещё требует формата, миграции и crash-recovery;
нельзя назвать общий OS-секрет доменным и раздать обеим полосам. Нельзя также
перенести пароль и расшифровку всего keyring в один broker, обслуживающий cover.
Нужно доказать раздельное получение разрешённых доменных ключей и совместимость
с криптографическим удалением, отсутствием повторного использования ключей и
откатом после сбоя. До этого существующее хранилище не мигрируется.

Создание, rotation/shred и удаление workspace требуют put/remove OS-секретов;
provider credentials имеют отдельный API. Эти операции не входят в согласованную
поверхность выдачи доменных ключей. Их нельзя молча добавить в RPC или сохранить
через привилегированный fallback core. Сначала необходимо отдельное согласованное
решение жизненного цикла хранилища; до него M6 остаётся открытым.

Брокер тоже обязан иметь профиль из репозитория, отсутствие внешней сети,
минимальные файлы и запрет произвольных children. Windows restricted token и
Job Object сами по себе этого не доказывают. Кандидат для проверки — отдельная
закреплённая identity с WFP-запретами до первого ResumeThread, без самостоятельно
запрашиваемого повышения прав. Необходимо проверить IPv4/IPv6 TCP/UDP, DNS через
системные службы, remote pipes и поведение при недоступности/перезапуске служб.
Пока нет положительного доказательства запрета всех каналов и безопасного
provisioning правил, такой broker нельзя подключать к production.

Linux должен использовать bwrap/seccomp и только необходимый локальный IPC к
Secret Service; весь session bus или HOME не выдаётся. Для транспорта сохраняется
production netns launcher ADR 0078/0082. Общий netd-профиль и разрешённый запуск
его PT требуют отдельной интеграции: нельзя разрешить произвольный spawn или
обойти изоляцию PT ADR 0085. Windows PT до фактической AppContainer-интеграции
остаётся запрещённым. Внешний browser stdio-переходник также остаётся открытой
границей критерия «каждый процесс». macOS и microVM вне этой задачи.

## Критерии приёмки

До подключения брокера обязательны реальные отрицательные OS-тесты сети,
чужих файлов и произвольных children, с положительным контролем разрешённого
domain key и фиксированного worker. Неверные полоса, домен, профиль, роль,
kernel PID, повтор кадра, отозванная сессия и подмена credential/binary должны
отвергаться до чтения ключа или spawn. Нужны проверки parent crash, отмены,
PID reuse, отсутствия открытых ключей на диске и в логах, migration/shred/recovery
и отсутствия пути cover → shadow. tor-pcap, linux-isolation-vm и
windows-object-owner сохраняют прежние строгие проверки. До их прохождения
два пункта THREAT_MODEL §9 не отмечаются выполненными.

Основания для Windows-кандидата: [restricted tokens](https://learn.microsoft.com/en-us/windows/win32/secauthz/restricted-tokens),
[WFP ALE layers](https://learn.microsoft.com/en-us/windows/win32/fwp/ale-layers).
Это направление исследования сетевой границы, а не подтверждённая реализация.
