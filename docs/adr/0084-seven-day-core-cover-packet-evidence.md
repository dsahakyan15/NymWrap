# Семь виртуальных дней core → nw-netd под OS pcap

## Решение

Обязательный CI job `tor-pcap` расширяет локальную сеть ADR 0064/0082,
не создавая новый транспорт. Координатор `core-cover-egress` собирается
как example `nw-core`: он использует настоящий Workspace, SQLCipher,
сохраняемый Scheduler и общий DailyBudget. Существующий `take_traffic_slot`
доступен как библиотечный метод для такого драйвера; IPC-команд, настроек
production и обходов авторизации не добавляется.

После 16 канареечных запросов M2 четыре независимых сценария проходят
семь виртуальных UTC-дней каждый: Poisson и Constant, каждый с ограничением
по числу (3 запроса, 14 microUSD) и по расходу (5 запросов, 10 microUSD).
Верхняя цена каждой попытки — 3 microUSD, поэтому разрешены ровно три
отправки в день. В слотах чередуются синтетические real/decoy; обе категории
проверяются Shield и одним shape, decoy использует production SendOnce.
Слот и общий бюджет сохраняются до IPC, затем вызываются production Client,
AEAD dispatcher и Tor/TLS/HTTP к локальному синтетическому provider.

Проверяются отсутствие слота до срока и повторного слота в ту же секунду,
переоткрытие Workspace после каждой доставки, два отказа сверх бюджета
за каждый день с повторным переоткрытием, отказ отката часов и возобновление
со следующего дня. Ключи тестового store живут только в LockedKey в памяти,
данные Workspace — в зашифрованном каталоге fscrypt и SQLCipher. Текст,
который обозначен real, тоже полностью синтетический.

## Независимая проверка и границы

Node oracle восстанавливает тела HTTP из настоящего tcpdump/tshark pcap,
сверяет SHA-256 и длину с квитанциями provider и учётом core. Он требует
ровно 100 запросов: прежние 16 и новые 84. Для каждого из 28 scenario/day
независимо пересчитывает число и сумму резервов по фиксированной тестовой
политике, требует исчерпания нужного лимита и полноты семи дней. Все пять
байтовых корзин должны встретиться отдельно у real и decoy в каждом режиме
и варианте лимита. Лишние/пропавшие пакеты, изменённые лимиты, сбросы счётчиков,
неверные слоты и канарейки делают проверку красной. Report и `cover-week.json`
публикуются вместе с pcap, synthetic TLS keys и хешами артефактов.

Первый CI-прогон 100 запросов (run 45753879448) создал обычный XML PDML
`provider.pdml` размером 47 524 910 байт при raw `provider.pcap` 1 763 074 байта:
это ожидаемое текстовое раскрытие полей tshark, а не рост сетевого захвата.
Предыдущий предел 32 MiB был рассчитан на 16 запросов. Для фиксированного набора
из 100 запросов установлен конечный предел 64 MiB одновременно до чтения файла
и перед разбором XML; DTD/ENTITY, неполные записи и лишние запросы по-прежнему
отвергаются. Предел не зависит от доступной памяти runner и не снимается.

Виртуальные часы передаются существующим API scheduler/budget; часы ОС и Tor
не меняются. Это проверка семидневного бюджета и корзин на выходе транспорта,
а не доказательство постоянного ритма пакетов в реальном времени. Новое
пакетное выравнивание не требуется для этих критериев SPEC §9; bootstrap,
TLS и задержки provider по-прежнему влияют на реальный ритм (ADR 0020).
Драйвер не проходит полный production Route, OS credential pool, локальную
генерацию модели, FIFO backend или UI-одобрение; их прежние проверки сохраняются.
Strict/paranoid с L3 не включаются. Новых зависимостей нет.

Локальные тесты драйвера и отрицательные проверки oracle доступны на всех
трёх ОС; Linux namespace/Tor pcap выполняется в CI. M3 закрывается только
после зелёного `tor-pcap` для нового кода, а не по локальной симуляции.
