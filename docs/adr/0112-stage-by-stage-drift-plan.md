# ADR 0112 — этапы плана Drift собирает код

Дата: 2026-11-28. Статус: принято координатором по запросу владельца 2026-11-28.
Изменяет SPEC §6 (шаг Plan: «до 3 попыток с обратной связью модели»).
Подготовлено агентом, не человеком.

## Контекст

Прежде модель одним вызовом писала весь план: 10 этапов по 5 действий, до
трёх попыток. На CPU этой Windows-машины ни одна закреплённая модель не давала
проходящий план. 0.5B копировала схему. Планы 1.5B и 3B укладывались во время
(42–83 с с грамматикой), но ходили по кругу: 3 отката, шаг 0,47–0,58 при
пределе 0,222, соседство ниже `cos_ends + 0,05`. 7B не укладывалась в жёсткий
лимит 110 с одного вызова. Лимиты 240 с и 110 с — граница защиты, их не меняем.

Сначала проверили вариант «модель пишет по одному этапу, получив цель этапа и
предыдущий этап». 1.5B и 3B не выдерживали заданную смесь тем: 1.5B повторяла
один и тот же этап, у 3B уже второй этап уходил на 0,34–0,40 при цели 0,11.
Повторы с кодом обратной связи этого не исправили.

## Решение

1. Модель пишет только короткие однотемные списки по фиксированной грамматике
   `StageV1` (тема, мост, 5 действий Google/YouTube). Списки: по одному на
   каждый подтверждённый интерес (не больше 4), по одному «мосту» от каждого
   интереса к легенде и два варианта по самой легенде. Для двух интересов это
   6 вызовов. Темы уходят в модель только после минимизации Shield.
2. Каждый ответ проверяется отдельно:
   - утечки: `leakcheck` и `⟨NW_` по сырому ответу и по каждому полю. Утечка
     сразу останавливает весь план с `shield_blocked`, до любых эмбеддингов;
   - схема и безопасность тем. При ошибке повторяется только этот вызов (не
     больше 3 раз) с кодом обратной связи, без эха текста модели.
3. Код встраивает все действия и считает позицию каждого на оси
   интересы → легенда (`nw_drift::math`). Затем сортирует их по позиции и
   заполняет этап k окном из 5 соседних действий. Начало окна сдвигается в
   темпе урока: (k−1)/(n−1) (`math::stage_targets`). Код урока не
   импортируется. Средняя позиция окон не убывает, соседние этапы делят
   действия. Тема этапа — тема списка, давшего больше всего действий; мост —
   тема предыдущего этапа.
4. Собранный план проходит **прежнюю итоговую проверку без изменений**:
   `Plan::validate`, все пороги `math::score` (соседство, шаг ≤ 2/(n−1),
   откаты, покрытие ≥ 0,7) и хеш для одобрения. Неудача —
   `plan_checks_failed`.

## Последствия

- Последнее слово за кодом (инвариант 3): темп и порядок задаёт код, модель
  только предлагает формулировки. Ни один порог не ослаблен; пороги отката и
  шага вынесены в общие константы `math`.
- 6–12 коротких вызовов вместо 1–3 длинных. Каждый укладывается в 110 с. В
  процессе план строится за 33 с на 1.5B и 74 с на 3B; через LPAC-воркер
  дольше, потому что модель загружается на каждый вызов.
- Соседние этапы могут повторять одно и то же действие; формулировки дня
  по-прежнему переписываются отдельно и одобряются.
- Последний этап не обязан дойти до позиции 1: прежняя проверка требует
  покрытия легенды, а не полного достижения.
- 0.5B по-прежнему честно получает `plan_checks_failed`.
- Грамматика `PlanV1` (весь план) заменена на `StageV1`.
