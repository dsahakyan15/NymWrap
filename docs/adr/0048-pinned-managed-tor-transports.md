# Закреплённые мосты Arti и Lyrebird

По SPEC §4.9.1 и ADR 0043 мосты подключаются через `tor-ptmgr =0.48.0`
и `arti-client =0.48.0` с pt-client. Единственный внешний PT — Lyrebird из
Tor Expert Bundle 16.0.1: один официальный бинарник реализует obfs4, snowflake
и webtunnel. `sha2 =0.10.9`, уже закреплённый workspace, используется nw-netd
для проверки бинарника. Версии и хеши входят в lock-файл и manifest; cargo-deny
обязателен. Произвольные команды, аргументы, пути, unmanaged SOCKS и автоматическое
получение мостов в runtime запрещены.

Адреса и параметры мостов хранятся только в зашифрованном Vault. Они проходят
ограниченную схему и парсер Arti; выбор транспорта входит в контекст разрешения
выхода. Значения приватных параметров дополнительно защищает Shield как Device,
они отсутствуют в ответе статуса. Изменение мостов отзывает прежние разрешения;
уже запущенный сетевой контекст требует Lock и повторного открытия.
Включённый мост обязателен: отсутствие бинарника, несовпадение SHA-256,
ошибка PT или bootstrap не разрешают прямой Tor или обычный HTTP как fallback.
Все PT принадлежат shadow и внутреннему сетевому компоненту nw-netd: получают
только Tor-поток и параметры моста, без vault, истории, ключа провайдера или
тела запроса. Их жизненный цикл и песочница должны охватываться той же границей
nw-netd; остальные процессы остаются без внешней сети. Это реализация явно
запрошенных пользователем PT-бинарников, не общий запуск сетевых программ.

Бинарники устанавливает отдельный build-скрипт из фиксированных официальных
архивов; runtime ничего не скачивает и не ищет исполняемые файлы в PATH.
Он сверяет размер и SHA-256 перед использованием. Windows держит read handle
без разрешения записи/удаления на время Tor. Состояние PT создаётся внутри
проверенной шифрованной директории транспорта. Изоляция процессов PT, запрет
пакетов в обход транспорта и отсутствие журналов с параметрами входят в
незакрытые приёмочные проверки M2/M3/M6.

В локальном tor-ptmgr исправлены наследование окружения и зависимость завершения
тихого дочернего процесса от чтения следующей stdout-строки. PT получает только
управляющие TOR_PT-переменные, нормализованные публичные значения и свой
зашифрованный каталог как HOME/TEMP; stderr отбрасывается. Drop немедленно
завершает и reaps ребёнка. См. vendor/tor-ptmgr/NYMWRAP-PATCH.md с upstream-хешем.
Регрессия tests/leak/src/pt_process.rs запускает настоящие синтетические процессы,
в том числе унаследованную канарейку и тихий PT; она прошла на Windows. Также
прошёл запуск закреплённого Lyrebird для всех трёх протоколов с проверкой закрытия
живого локального слушателя при Drop. Это проверка запуска и lifetime без
соединения с мостом, не доказательство успешного bridge bootstrap.

Linux CI создаёт отдельный временный ext4 с fscrypt v2. Маленький CI-only C helper
генерирует 64 байта getrandom, блокирует их в памяти, передаёт ключ ioctl ядру
и затирает его; ключ не сохраняется в файле/argv. Teardown снимает mount и удаляет
только созданный образ и пустые каталоги. Этот job на данном Windows-хосте
не проводился и до зелёного CI не считается выполненным.

Происхождение пинов: [официальный подписанный список Tor 16.0.1](https://dist.torproject.org/torbrowser/16.0.1/sha256sums-signed-build.txt).
Локальный GPG verify прошёл 2026-11-23: primary
EF6E286DDA85EA2A4BA7DE684E2C6E8793298290, signing subkey
022DA248432D2A0E0F54E65E316C1FACD62D07D9. Отпечаток primary сверяется
с [инструкцией Tor](https://support.torproject.org/tor-browser/getting-started/verifying-tor-browser/).
Архивы пяти desktop-платформ загружены, их хеши сверены с этим списком, хеш
Lyrebird получен из точного tar member без исполнения. Источник возможностей —
[документация Tor](https://support.torproject.org/little-t-tor/circumvention/using-bridges/)
и локальный исходный код закреплённого Arti. Зелёный CI, реальный PT lifecycle
и pcap требуются отдельно; подпись upstream не является подписью релиза NymWrap.
