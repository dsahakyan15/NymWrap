# Сессионная авторизация shadow RPC и роль API

## Причина

Канареечная регрессия `unapproved_same_user_shadow_client_cannot_read_unlocked_secrets`
воспроизводит чтение открытого vault посторонним процессом того же пользователя.
ACL сокета проверяет пользователя, но не разрешает клиенту читать секреты.
Список имён исполняемых файлов также не доказывает разрешение экземпляра.

## Решение

Desktop запускает свой core и передаёт свежий случайный ключ 256 бит только
через наследуемый stdin. Core запускает свой API с другим ключом через такой
же канал. Ключи остаются в locked/zeroized памяти; их нет в argv, окружении,
файлах или журналах. Произвольный `nymwrap rpc` больше не получает привилегии
открытой desktop-сессии. Старый неавторизованный протокол отвергается.

Bootstrap читает собственный read-only duplicate stdin pipe без общего буфера
`std::io::Stdin`, который сохранял бы дополнительную незанулённую копию ключа.
Обычный файл, null device и консоль отвергаются. Duplicate не наследуется
следующими процессами: Windows DuplicateHandle с bInheritHandle=false,
Unix F_DUPFD_CLOEXEC. Windows API добавляет только feature Console к уже
закреплённому windows-sys 0.61.2. Native regression проверяет read/write права
и отказы file/null; межпроцессный тест проверяет настоящий bootstrap core/API.
Первоначальные 32 байта ключа nw-netd тоже читаются этим дескриптором;
буфер stdin для ключа транспорта больше не используется. Протокол egress
и его последовательности сообщений не изменены.

Принимающий core связывает роль с kernel PID клиента и ключом. Desktop
дополнительно проверяет kernel PID core по сохранённому объекту запущенного
child и его liveness, API — по bootstrap своего родителя. На каждое соединение
core выдаёт новый случайный challenge. Один запрос и один ответ шифруются
XChaCha20-Poly1305 с разными AAD для направления и роли, привязанными к этому
challenge. Поэтому запись из прошлого соединения и отражение ответа не
авторизуют новый запрос. Используется уже закреплённая зависимость
chacha20poly1305 0.10.1; nw-core получает прямую зависимость от неё.

Windows namespace pipe включает SID пользователя и настроенный LOCALAPPDATA,
хешированные с разделителем домена. Общий helper в nw-ipc использует уже
закреплённый sha2 0.10.9, который раньше напрямую использовал nw-bridge.
Это позволяет проверять настоящие демоны в отдельном синтетическом экземпляре,
не занимая endpoint работающей пользовательской установки. Старые endpoint
на одном SID не подхватываются. Путь data root не передаётся в имени открыто;
неизвестный namespace не выдаёт полномочия без сессионного ключа.

Control может выполнять существующие команды UI. Роль API получает только
чат, embeddings и операции submit/status/cancel фонового запроса. Она не может
читать vault, сводку импорта или чужую историю, менять политику, одобрять
отправку, управлять ключами, планами или удалением. Решение проверяет код
перед dispatch. Публичного способа повысить роль нет.

Потеря stdin родителя запускает обычное закрытие сессии: ключи блокируются
или выполняется ранее разрешённый хвост standard. Сам API завершается при
потере родителя и при остановке core. Повторная отправка запросов при потере
соединения не выполняется. Неизвестный клиент отсеивается до чтения команды;
handshake авторизованного PID ограничен по времени и размеру.

## Ограничения

Это защита работающего RPC от неразрешённого экземпляра, а не закрытие всего
A6. Изоляция процессов/памяти и доступ того же пользователя к OS credential
store остаются отдельными открытыми критериями M6. Украденная память
авторизованного клиента или его выполнение скомпрометированы вместе с ролью.
Запуск своей копии core не даёт доступа к ключу уже работающей сессии, но
защита OS keyring от локального ПО ещё не доказана.

Новая UI не подхватывает ключ другой или прежней UI. Если после её закрытия
ещё работает согласованный хвост, новая сессия должна дождаться освобождения
endpoint. Автоматическое восстановление привилегий через файл или произвольный
same-user IPC не добавляется. Удобное безопасное восстановление требует
отдельного решения о присутствии пользователя и остаётся ограничением.

Приёмка этой части: исходная канареечная регрессия включена в обычные тесты;
control работает, API отвергает привилегированные команды; неправильный ключ,
replay/challenge, направление и неподтверждённый сервер отвергаются. Нужны
реальные межпроцессные проверки bootstrap и полные зелёные CI всех ОС.
Частичные или только unit-прогоны не закрывают M6.
