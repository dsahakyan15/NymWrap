# Сохраняемые квитанции идемпотентности HTTP submit

## Решение

Только POST `/v1/nymwrap/chat/jobs` принимает необязательный `Idempotency-Key`:
16–128 ASCII букв, цифр, `-_.`. Синхронные chat/embeddings и остальные endpoints
отвергают этот заголовок, чтобы клиент не считал их защищёнными от повторов.
Дубли заголовка запрещены. Ключ не передаётся модели, провайдеру, netd или в ответ.
Приватный RPC принимает ключ как Sensitive; при хешировании он zeroize.

До вызова модели core сохраняет в зашифрованном Vault SHA-256 ключа,
отпечаток conversation/messages/max_tokens/min_trust и состояние Pending.
Неуказанный max_tokens нормализуется к 2048; температура не входит в отпечаток,
поскольку она не управляет локальной детерминированной подготовкой или отправкой.
Изменение ввода с прежним ключом даёт 409 idempotency_conflict.

Ссылка на remote job записывается до spawn отправителя. Повтор возвращает текущее
состояние того же задания, включая Cancelled/Uncertain; повтор send не вызывается.
Локальный L0-ответ хранится отдельно в ShadowHistory и возвращается без inference.
Сохранённая ошибка также возвращается без повторения подготовки. Pending после
потери соединения/остановки — 409 idempotency_uncertain, даже если отправка могла
ещё не начаться. Это консервативная гарантия at-most-once, а не exactly-once.
Смена настроек или обязательного просмотра не разрешает заново исполнить ключ;
чтение старого результата ничего не отправляет и не одобряет.

Квитанции не вытесняются и не истекают автоматически. После удаления истории или
вытеснения job остаётся tombstone: 410 idempotency_expired. Максимум — 8192 ключа
на пространство; затем 429 idempotency_capacity для новых ключей. Существующие
продолжают работать. Удаление домена Vault/всего пространства уничтожает квитанции
вместе с его ключом. Клиент должен хранить случайный ключ до получения результата
и не создавать новый ключ для неопределённой попытки.

## Проверки

Тесты покрывают строгий HTTP-заголовок, изменение параметров/доверия, Pending
после reopen, L0 без модели, tombstone, отсутствие ключа в исходящем HTTP и
зашифрованное хранение. E2E использует настоящий core/CPU/HTTP: конкурентные
повторы очереди, отмену, L0 и повтор обоих результатов после перезапуска.
Зависимостей не добавлено; восемь инвариантов сохранены.
