# Готовность локального Tor до первой отправки

На 6985640 Chutney сообщил `Everything bootstrapped`, но первый `Tor::send`
завершился `tor_connect_failed` за 2,26 с. Готовность релеев не гарантирует, что
Arti уже получил пригодный exit consensus. Test-only fixture после bootstrap
открывает поток через отдельный изолированный Tor-клиент к `api.example.test:443`:
до 10 попыток по 8 с, пауза 2 с между неудачами (не более 98 с). Успешный поток
сразу закрывается без TLS/HTTP и без секретов. Bootstrap вместе с ожиданием
ограничен прежними 180 с, внутри 190-секундного Initialize IPC deadline.

Общий helper используется процессным worker и библиотечным pcap-тестом.
Повторы допустимы только до первого настоящего запроса: production transport,
16 однократных отправок, независимый packet oracle и проверка остановки Tor
не меняются. После остановки процессный сценарий требует явный AEAD-ответ
`remote_request_failed` при живом provider; таймаут остаётся провалом.
Регрессии проверяют позднюю готовность, исчерпание попыток и зависший connect.

Текущий процессный CI дополнительно выявил `EADDRNOTAVAIL` при IPv6 connect
из пустого core netns: ядро не смогло выбрать исходный адрес ещё до поиска
маршрута. Probe допускает этот код только для IPv6, а `ENETUNREACH` — для обеих
семей. Успешное соединение и таймаут остаются провалом; проверка seccomp внутри
core по-прежнему требует точный `PermissionDenied` для TCP/UDP IPv4/IPv6.

Закрытие M2 ограничено Linux-критериями SPEC §9 и требует трёх последовательных
зелёных `tor-pcap` в CI. Production launcher и реальный startup core проверяются,
но полный core/model/approval pipeline не заявляется. Изоляция core/netd на
Windows/macOS, полная файловая песочница Linux и установщик службы/coordinator
GUI остаются долгами M6 (ADR 0082); новых зависимостей и runtime-настроек нет.
