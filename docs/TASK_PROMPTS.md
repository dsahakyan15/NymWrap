# Промпты для агентов: оставшаяся работа по NymWrap

Как пользоваться:

1. **Один промпт — один новый тред.** Не продолжай старый длинный тред и не
   используй один `/goal` на все этапы.
2. В новый тред вставляй **сначала «Общую шапку»**, потом **одну задачу**.
3. Задачи идут по порядку: следующая опирается на предыдущую.
4. Когда агент закончил, проверь, что он обновил `docs/IMPLEMENTATION.md` и сделал
   коммит, и только потом открывай следующий тред.
5. Если задача не закончена за один тред, открой новый тред с той же задачей.
   Агент продолжит по `docs/IMPLEMENTATION.md`.

## Шаг 0 — сделать самому (агент этого не может)

      (failed payment или spending limit). Без этого CI не запускается, и по

      Альтернативы: сделать репозиторий публичным (для публичных репозиториев
      Actions бесплатны; сначала проверь, что там нет личных данных) или
      подключить self-hosted runner.

      и проверка на настоящих аккаунтах (её делаешь ты по
      `docs/ACCOUNT_ADAPTER_CHECKLIST.md`).

## Общая шапка (вставлять в начало КАЖДОГО треда)

```text
Контекст проекта. NymWrap — мой школьный проект по защите приватности. Это
защитная программа: она работает только на моём компьютере, с моими данными и
моими аккаунтами. Её цель — чтобы мои личные данные не уходили к сервисам.

В репозитории есть тесты, которые звучат «атакующе», но они защитные:
- «канарейки» — синтетические фальшивые секреты; тест проверяет, что они НЕ
  выходят наружу;
- «оценщик связываемости» / «атакующая модель» — это измерение из модели угроз
  (docs/THREAT_MODEL.md): мы проверяем, что защита не даёт сопоставить запрос
  с синтетическим досье;
- проверки песочниц, namespace и сброса привилегий нужны, чтобы собственные
  процессы NymWrap работали с минимальными правами;
- фаззинг и pcap запускаются только на нашем коде и нашем локальном трафике.
Все тестовые данные синтетические. Программа не обходит CAPTCHA, не подделывает
отпечаток браузера, не трогает чужие системы и чужие аккаунты.

Правила работы:
- Прочитай AGENTS.md (инварианты), затем разделы docs/SPEC.md,
  docs/THREAT_MODEL.md и docs/adr/, указанные в задаче. Текущее состояние —
  в docs/IMPLEMENTATION.md.
- Делай ТОЛЬКО одну задачу ниже. Не начинай другие этапы.
- Перед концом: cargo test --workspace, cargo clippy -- -D warnings, тесты
  утечек (tests/leak), тесты расширения и app — зелёные. Если что-то не удалось
  проверить, так и напиши.
- Локальные проверки не считаются зелёным CI. Не отмечай этап закрытым без CI.
- В конце: обнови docs/IMPLEMENTATION.md, при новом решении добавь ADR, сделай
  один коммит и остановись.
- Последнее сообщение: 1) что сделано; 2) что проверено и где (локально или в
  CI); 3) что осталось; 4) что должен сделать я сам.

Задача:
```

## Задачи

### 1. CI: снова получить зелёный прогон

```text
Задача 1 — CI. GitHub Actions снова доступен (я восстановил оплату). Запусти
workflow ci.yml на текущем HEAD, дождись результата через gh и почини все
красные задания. Не ослабляй проверки и не помечай их как allowed-failure,
чтобы получить зелёный результат. Готово, когда ci.yml зелёный на всех 3 ОС.
Запиши номер run в docs/IMPLEMENTATION.md.
Читать: AGENTS.md, .github/workflows/ci.yml, docs/IMPLEMENTATION.md (блок про CI).
```

### 2. M2 — сеть: namespace для nw-netd

```text
Задача 2 — закрыть M2 (SPEC §9, §4.5; ADR 0077, 0078). Подключи уже
подготовленный запуск nw-netd в отдельном network namespace (Client::spawn_prepared)
к production launcher на Linux. Нужны интеграционные тесты:
(а) core в своём namespace не может открыть внешний сокет;
(б) если Tor остановлен, запрос завершается ошибкой и напрямую ничего не уходит;
(в) два разговора идут через две разные цепочки.
Тесты должны идти в CI. Windows и macOS — честно описать, что там даёт ОС и чего нет.
Читать: SPEC §3.1, §4.5, §9 (M2); THREAT_MODEL §3, §7; ADR 0077, 0078.
```

### 3. M3 — cover-трафик: проверка по захвату

```text
Задача 3 — закрыть M3 (SPEC §4.3, §9). Добавь в CI сквозной тест между
процессами core → nw-netd с локальной тестовой Tor-сетью: запиши трафик на выходе
nw-netd (pcap) и проверь, что длины запросов лежат только в разрешённых корзинах,
а бюджет не превышается за симулированные 7 дней. Используй только локальный
синтетический трафик. Добавь пакетный ритм, если без него критерий не выполняется.
Читать: SPEC §4.3, §9 (M3); docs/IMPLEMENTATION.md (pcap, cover traffic).
```

### 4. M3H — данные устройства: доделать остаток

```text
Задача 4 — M3H (SPEC §4.9, ADR 0043–0048). Доделай пункты из колонки
«Остаётся» в docs/IMPLEMENTATION.md для «Жёсткие данные»: полнота nw-probe на
Windows/macOS (недоступные источники явно помечены «неизвестно», fail-closed);
хвост сеанса для strict/paranoid; bootstrap мостов и изоляция процесса PT;
автоматическая проверка гигиены. Критерий: канарейки каждого вида секретов
устройства и каждого детектора не появляются в захвате на границе nw-netd; golden
заголовков и ClientHello совпадает на Windows и Linux в CI.
Читать: SPEC §4.9 целиком, §9 (M3H); ADR 0043–0048.
```

### 5. Shield: независимая оценка linkcheck

```text
Задача 5 — оценка Shield/linkcheck (SPEC §4.1.1; ADR 0040, 0065–0072).
Цель: измерить, что защита не даёт сопоставить отправленный текст с
синтетическим досье пользователя. Сделай независимый split (development отдельно
от held-out), заморозь пороги на development, потом один раз прогони held-out и
запиши отчёт: долю L0, отказы, полезность ответов, точность оценщика
связываемости относительно случайной. Не меняй пороги после held-out. Все данные
синтетические, EN/RU/HY.
Читать: SPEC §4.1, §4.1.1; ADR 0040, 0065–0072; docs/IMPLEMENTATION.md (Linkcheck).
```

### 6. Сеть: очередь paranoid

```text
Задача 6 — профиль paranoid в сети (SPEC §4.7, §8). Реализуй очередь paranoid:
реальные запросы отправляются только в слотах cover-трафика, маршрут не слабее
указанного в SPEC, при недоступности маршрута — отказ, а не понижение уровня.
Тесты: нет отправки вне слота; нет понижения маршрута; Uncertain не повторяется.
Читать: SPEC §4.3, §4.7, §8; THREAT_MODEL §3.
```

### 7. M6 — песочницы для остальных процессов

```text
Задача 7 — M6, песочницы (THREAT_MODEL §7, §9). Чек-лист: «каждый процесс
запускается только через nw-sandbox с профилем из репозитория» и «процессы, кроме
nw-netd, не могут открыть внешний сокет». Доделай это для оставшихся процессов
Windows (LPAC/AppContainer) и демонов Linux (bwrap + seccomp). Для каждого
процесса — отрицательный тест (сеть, файлы вне разрешённых, запуск дочерних).
macOS не трогай, это задача 8.
Читать: THREAT_MODEL §7, §9; SPEC §3.1, §4.8; ADR про песочницы в docs/adr/.
```

### 8. M6 — macOS App Sandbox

```text
Задача 8 — M6, macOS. Добавь профили App Sandbox (entitlements) для процессов
NymWrap на macOS: сеть только у nw-netd, без capability геолокации и Wi-Fi.
Тесты в CI на macos-latest: отказ сети и чтения файлов вне контейнера.
Читать: THREAT_MODEL §7, §9; SPEC §3.1.
```

### 9. M6 — cargo-vet

```text
Задача 9 — M6, cargo-vet. Сделай cargo-vet зелёным для всех четырёх графов
зависимостей. Сначала подключи доверенные внешние наборы аудитов (imports), потом
просмотри оставшиеся дельты. Каждый собственный аудит помечай как выполненный
агентом. Не используй массовые exemptions, чтобы просто получить зелёный результат:
каждое исключение — с причиной. Если работы слишком много для одного треда,
сделай один граф и остановись.
Читать: AGENTS.md (зависимости); ADR 0073; supply-chain/ в репозитории.
```

### 10. M6 — фаззинг 24 часа

```text
Задача 10 — M6, фаззинг. Запусти уже подготовленную кампанию
fuzz-campaign.yml (импортёры и IPC, 24 часа на каждую цель) и дождись результата.

Читать: .github/workflows/fuzz-campaign*.yml; ADR 0070.
```

### 12. M6 — MicroVM для агентов

```text
Задача 12 — M6, MicroVM (SPEC §4.8). Добавь вариант запуска агента в MicroVM
```

### 13. M5 — Drift на синтетических страницах

```text
Задача 13 — M5/Drift (SPEC §6). Настоящие аккаунты не трогать. Доделай адаптеры
расширения для видео и ИИ-сервисов только на синтетических локальных HTTPS-страницах,

включается только явно, с предупреждением (SPEC §6.2). Никакой подмены отпечатка.

Читать: SPEC §6 целиком; AGENTS.md инвариант 7.
```
